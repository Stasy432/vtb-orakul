# ВТБ.Оракул — прогнозирование и управление рисками бизнеса

**Команда:** «Ставка на успех»  
**Участник:** Савельев Никита — Frontend / Backend-разработчик  
**Статус:** демонстрационный MVP для «Академии Финтеха»

## 1. О проекте

ВТБ.Оракул — прототип интеллектуального помощника для малого бизнеса, который моделирует движение денежных средств, выявляет потенциальные кассовые разрывы и позволяет сравнивать варианты финансовых действий.

Основная задача MVP — показать предпринимателю не только будущий остаток денежных средств, но и возможные последствия изменения сроков платежей и поступлений.

Все финансовые данные в текущей версии демонстрационные. Продукт не является официальным сервисом ВТБ и не выполняет реальные финансовые операции.

## 2. Реализованные функции

- Отображение текущего денежного остатка, поступлений и планируемых платежей.
- Прогноз денежных остатков на 14 и 30 календарных дней.
- Выявление первого отрицательного остатка и минимального остатка на горизонте.
- Сравнение трёх сценариев: без изменений, перенос части платежа и ускорение поступления.
- Изменение начального остатка, резервного порога, сумм и дат основных операций.
- Сохранение выбранного сценария и возврат к исходному плану.
- Экспорт дневного прогноза в CSV.
- Демонстрационный помощник, объясняющий финансовый риск на основе расчётных правил.

## 3. Техническая архитектура

Текущая версия представляет собой клиентское веб-приложение.

**Технологии:**
- HTML5 — структура страниц.
- CSS3 — оформление интерфейса и адаптивная компоновка.
- JavaScript — финансовые расчёты, обработка действий пользователя и переключение экранов.
- LocalStorage — сохранение состояния приложения в браузере.
- CSV — экспорт результатов прогноза.
- GitHub Pages — публикация демонстрационной версии.

Основная логика интерфейса и расчётов находится в файле `index.html`. Для запуска текущего прототипа отдельный серверный backend не требуется.

## 4. Алгоритм расчёта

Расчёт выполняется по календарным дням. Для каждого дня учитываются поступления и платежи, после чего рассчитывается остаток на конец дня.

**Формула:**

Остаток на конец дня = остаток на начало дня + поступления за день − платежи за день.

Минимальный остаток определяется как наименьшее значение дневного остатка на выбранном горизонте.

Первый дефицит — первая дата, на которую прогнозируемый остаток становится отрицательным.

Резервный порог используется для дополнительной оценки ликвидности: положительный остаток может оказаться ниже установленного пользователем резерва.

## 5. Сценарное моделирование

### Сценарий A — без изменений

Используются исходные даты и суммы. Сценарий показывает риск, возникающий при оплате поставщику до ожидаемого поступления от клиента.

### Сценарий B — перенос части платежа

Часть обязательства переносится на выбранную дату. Общая сумма обязательства не меняется. Моделирование предполагает согласование новых условий с поставщиком.

### Сценарий C — ускорение поступления

Дата ожидаемого поступления переносится на более ранний день. Сумма поступления остаётся неизменной. Реальное зачисление денег не гарантируется.

## 6. Результаты ручного тестирования

В ходе проверки демонстрационной модели использовались различные значения начального остатка и платежа.

| Проверка | Результат |
|---|---|
| Изменение начального остатка с 1 000 000 до 1 200 000 ₽ | Расчёт пересчитан корректно |
| Изменение платежа на 1 700 000 ₽ | Минимальный остаток −700 000 ₽, конечный +100 000 ₽ |
| Изменение платежа на 1 200 000 ₽ | Минимальный остаток −200 000 ₽, конечный +600 000 ₽ |
| Сценарий C: поступление 28 октября | Минимальный остаток +600 000 ₽, отрицательного остатка нет |
| Сохранение и сброс выбранного сценария | Проверено вручную |
| Горизонт 30 дней | Экспорт охватывает период с 24 октября по 22 ноября 2026 года |
| Экспорт CSV выбранного сценария | Даты, суммы и дневные остатки сверены с интерфейсом |

Проверки выполнялись на демонстрационных данных. Они подтверждают корректность проверенных сценариев, но не заменяют автоматизированные тесты и полное тестирование граничных случаев.

## 7. Ограничения текущей версии

- Используются условные данные, а не банковские выписки.
- Даты поступлений не подтверждаются автоматически.
- Перенос платежей и ускорение поступлений являются сценарными допущениями.
- AI-помощник работает на основе заранее заданных правил и расчётов; внешняя нейросеть не подключена.
- Нет интеграции с банковскими системами и автоматического исполнения платежей.
- Для дальнейшего развития необходимы автоматизированные тесты, обработка дополнительных операций и расширение проверки финансовых рисков.
